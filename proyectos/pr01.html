01 / RESUMEN EJECUTIVO

Estado actual del walkthrough

El proyecto aplica los conocimientos de seguridad informática a la evaluación controlada de una máquina virtual deliberadamente vulnerable. Kali Linux funciona como estación de análisis y SNAKEOIL como único objetivo autorizado; ambas máquinas operan dentro de una red privada de VirtualBox sin exposición a Internet.

Se completaron la preparación del laboratorio, la identificación de direcciones, el descubrimiento del objetivo, el escaneo de los 65,535 puertos TCP, el reconocimiento web y la enumeración manual y automática. La validación no destructiva confirmó la superficie de entrada de la aplicación, pero todavía no se ha realizado explotación, acceso inicial ni escalamiento de privilegios.

Resultado principal: SNAKEOIL fue identificada en 192.168.56.103 con los puertos 22, 80 y 8080 abiertos. El servicio web del puerto 8080 concentra los hallazgos actuales.

02 / OBJETIVOS

Aplicar teoría mediante una evaluación reproducible

El objetivo general es demostrar la aplicación práctica de técnicas y metodologías de seguridad mediante un walkthrough detallado, seguro y documentado de una máquina virtual vulnerable.

  • Configurar un entorno de virtualización aislado para realizar las pruebas de forma segura.
  • Descubrir el sistema objetivo e identificar puertos, servicios y versiones expuestas.
  • Enumerar aplicaciones, recursos y mecanismos de autenticación para construir hipótesis técnicas.
  • Investigar vulnerabilidades y evaluar su viabilidad antes de seleccionar una prueba de concepto.
  • Documentar, si procede, el acceso inicial, la post-explotación y el escalamiento de privilegios.
  • Registrar comandos, resultados, capturas, riesgos, mitigaciones y aprendizajes.
  • Preparar un informe final y un video explicativo del recorrido completo.

03 / ALCANCE Y LABORATORIO

Topología aislada y límites de la práctica

Estación de análisis

Kali Linux en 192.168.56.104/24.

Sistema objetivo

digitalworld.local SNAKEOIL en 192.168.56.103.

Segmento virtual

Red 192.168.56.0/24 configurada como solo-anfitrión.

Virtualización

Oracle VirtualBox con ambas máquinas conectadas al mismo adaptador privado.

Sistema identificado

Objetivo Linux basado en Debian 10; detección aproximada mediante Nmap.

Límite autorizado

Las pruebas se restringen a la máquina local de práctica y no incluyen sistemas externos.

Control de seguridad: SNAKEOIL no utiliza modo puente ni NAT. Los adaptadores adicionales permanecen desactivados y el modo promiscuo está denegado.

Acciones ejecutadas y finalidad

Identificación de Kaliip -br addr

Consulta resumida de interfaces, estado y prefijo de red.

Descubrimiento del segmentosudo nmap -sn 192.168.56.0/24

Identificación de hosts activos sin escaneo de puertos.

Escaneo completo del objetivosudo nmap -sS -sV -sC -O -p- 192.168.56.103 -oN snakeoil_escaneo_completo.txt

Revisión de todos los puertos TCP, versiones, scripts básicos y sistema operativo aproximado.

Enumeración de contenido webgobuster dir -u http://192.168.56.103:8080 -w /usr/share/wordlists/dirb/common.txt -x txt,html,py -o gobuster_8080.txt

Búsqueda de rutas y archivos no enlazados desde la interfaz.

Validación no destructivacurl -sS -i http://192.168.56.103:8080/<ruta>

Inspección de encabezados y respuestas de /users, /registration, /create, /test y /secret.

Métodos permitidoscurl -sS -i -X OPTIONS http://192.168.56.103:8080/<login|run>

Caracterización de los endpoints sin ejecutar su operación principal.

06 / PUERTOS Y SERVICIOS

Superficie inicial identificada

22/TCP · SSH

OpenSSH 7.9p1 Debian 10+deb10u2. Servicio de acceso remoto que requiere autenticación.

80/TCP · HTTP

nginx 1.14.2. Página estática de bienvenida que confirma la configuración de SNAKEOIL.

8080/TCP · HTTP

nginx 1.14.2. Aplicación Good Tech Inc.'s Snake Oil Project y principal superficie de análisis.

Plataforma

Nmap estimó un sistema Linux; la máquina inició sobre Debian 10 dentro de VirtualBox.

Criterio técnico: una versión observada no demuestra por sí sola una vulnerabilidad. Cada posible debilidad debe correlacionarse con la configuración real y validarse dentro del laboratorio.

La secuencia de recursos y las pistas tecnológicas orientan el análisis de autenticación y manejo de contenido, pero no constituyen por sí mismas una explotación confirmada.

08 / ENUMERACIÓN DE ENDPOINTS

Rutas descubiertas en el puerto 8080

/create · 200

GET devuelve una vista HTML titulada Create a New Post. No se enviaron ni guardaron datos.

/login · 405

GET no está permitido; OPTIONS declara POST y OPTIONS.

/registration · 200

GET devuelve JSON con el mensaje Wrong Method!!!, aunque el transporte responde 200.

/run · 405

GET no está permitido; OPTIONS declara POST y OPTIONS. No se enviaron comandos.

/secret · 500

GET produce un error interno con una respuesta JSON genérica.

/test · 200

GET devuelve el objeto JSON {"TestValue": 0}.

/users · 200

GET expone sin autenticación aparente el usuario patrick y un hash PBKDF2-SHA256.

Protección de datos: el valor completo del hash se conserva únicamente en la evidencia del laboratorio y no se transcribe en esta página pública.

09 / HALLAZGOS PRELIMINARES

Evidencia confirmada y límites de interpretación

F-01 · Exposición en /users

Divulgación confirmada de un nombre de usuario y material de autenticación. Severidad preliminar: media.

F-02 · Error en /secret

Respuesta HTTP 500 reproducible. Requiere más validación; un error aislado no prueba impacto explotable.

F-03 · Superficie POST

/login y /run aceptan POST, pero todavía se desconocen campos, validaciones y controles JWT.

Estado de explotación

No se ha recuperado ninguna contraseña, enviado una carga útil, ejecutado comandos ni obtenido acceso al sistema.

10 / RIESGOS Y MITIGACIONES

Controles defensivos recomendados

  • Exigir autenticación y autorización antes de consultar listados de usuarios.
  • Excluir hashes y cualquier material de autenticación de las respuestas de la API.
  • Aplicar códigos HTTP coherentes y mensajes de error mínimos para el cliente.
  • Registrar excepciones detalladas solo en el servidor y evitar trazas o datos internos en producción.
  • Validar estrictamente los cuerpos POST y limitar las funciones de creación y ejecución por rol.
  • Revisar expiración, firma, almacenamiento y revocación de tokens JWT.
  • Aplicar mínimo privilegio al servicio web y mantener nginx, OpenSSH y dependencias actualizados.

13 / SIGUIENTES PASOS

Continuación controlada del proyecto

  1. Crear o verificar una instantánea y confirmar nuevamente la IP del objetivo.
  2. Auditar el hash de forma offline dentro del laboratorio y documentar el resultado sin publicar credenciales.
  3. Caracterizar los formatos POST de registro, inicio de sesión y ejecución.
  4. Seleccionar una sola hipótesis sustentada y validar una prueba de concepto reproducible.
  5. Si se obtiene acceso, registrar usuario, host, privilegios y vector de escalamiento con evidencia mínima.
  6. Evaluar el impacto, completar las fases pendientes y actualizar el reporte con los resultados definitivos.
  7. Comprobar antes de la entrega que el enlace institucional del video mantenga permisos de visualización.

14 / CONCLUSIÓN Y REFLEXIÓN

Observar, comprobar y documentar

El laboratorio quedó correctamente segmentado y la superficie inicial se redujo a tres servicios TCP. La aplicación del puerto 8080 permitió confirmar una exposición de información en /users y caracterizar varios endpoints sin ejecutar acciones destructivas.

El principal aprendizaje es separar las pistas de los hallazgos confirmados: descubrir una ruta, versión o respuesta anómala orienta la investigación, pero no basta para afirmar que existe una vulnerabilidad explotable. Mantener el alcance aislado, registrar cada comando y reconocer los límites de la evidencia hace que el walkthrough sea seguro, honesto y reproducible.
