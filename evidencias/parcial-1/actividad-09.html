Actividad 09 · Laboratorio FPT 03

Bypass por eliminación no recursiva

Documentación del laboratorio “File path traversal, traversal sequences stripped non-recursively”: análisis del saneamiento incompleto, construcción controlada del payload y validación de la lectura de /etc/passwd.

  • Estado: completado
  • Fecha: 23/09/2026
  • Nivel: Practitioner
  • Evidencias: 8 capturas

01 / OBJETIVO

Evadir un filtro que elimina ../ una sola vez

La práctica consistió en identificar la solicitud que carga las imágenes de producto y comprobar que el filtro quitaba las secuencias de traversal sin volver a revisar el resultado. El objetivo técnico fue recuperar /etc/passwd mediante el parámetro filename y confirmar la resolución oficial del laboratorio.

Entorno autorizado: la prueba se realizó exclusivamente dentro del laboratorio interactivo de PortSwigger Web Security Academy. El procedimiento se documenta con fines académicos y defensivos.

02 / FUNDAMENTACIÓN TÉCNICA

El filtro transforma la entrada, pero no valida el resultado

La aplicación intenta sanear filename eliminando el patrón ../. El problema es que la operación se ejecuta una sola vez. En una cadena como ....//, al retirar la coincidencia interna, los caracteres restantes vuelven a formar un ../ funcional que ya no es analizado.

Clasificación

La falla corresponde a CWE-22 y se relaciona con OWASP A01: Broken Access Control, porque la entrada termina apuntando fuera del directorio permitido.

Causa raíz

El saneamiento modifica la cadena original, pero no repite la validación ni canonicaliza la ruta final antes de abrir el archivo solicitado.

Impacto CIA

La prueba afecta la confidencialidad al exponer un archivo del sistema. En funciones equivalentes de escritura o eliminación, también podría afectar integridad y disponibilidad.

Diferencia con FPT 02

FPT 02 empleó una ruta absoluta. FPT 03 conserva el enfoque relativo, pero anida caracteres para que el patrón reaparezca después del filtrado.

03 / PROCEDIMIENTO · PREPARACIÓN

Acceso al reto y generación de tráfico

  1. Iniciar el entorno: se abrió Burp Suite Community Edition con un proyecto temporal y su configuración predeterminada.
  2. Abrir el navegador integrado: desde Proxy se utilizó el navegador de Burp para enrutar automáticamente las solicitudes del laboratorio.
  3. Leer la consigna: PortSwigger indicó que la aplicación elimina las secuencias de traversal antes de usar filename y que la meta era recuperar /etc/passwd.
  4. Acceder a la tienda: se recorrieron los productos para provocar solicitudes de imágenes y registrar tráfico suficiente en HTTP history.

04 / PROCEDIMIENTO · CAPTURA

Corrección del filtro y selección de filename

  1. Detectar el problema: la configuración inicial de HTTP history ocultaba CSS, imágenes y extensiones específicas, por lo que las peticiones relevantes no aparecían.
  2. Corregir el filtro: se habilitó el tipo MIME de imágenes y se dejó vacío el campo de extensiones ocultas.
  3. Localizar la solicitud: se seleccionó GET /image?filename=46.jpg dentro de las peticiones visibles.
  4. Enviar a Repeater: desde el menú contextual se copió la petición a Repeater para editarla y reenviarla de forma controlada.

05 / PROCEDIMIENTO · EXPLOTACIÓN

Construcción del payload anidado y validación

  1. Conservar una línea base: Repeater recibió la solicitud original GET /image?filename=46.jpg.
  2. Modificar únicamente la entrada: el valor de filename se reemplazó por ....//....//....//etc/passwd.
  3. Enviar la petición: el servidor devolvió HTTP/2 200 OK y líneas con el formato característico del archivo de cuentas de Linux.
  4. Comprobar el resultado: al actualizar la página oficial, el indicador cambió de Not solved a Solved.

06 / EXPLICACIÓN DEL PAYLOAD

....//....//....//etc/passwd

....//

Cada bloque contiene una coincidencia interna ../. Cuando el filtro la elimina, los puntos y barras restantes se recombinan y generan otro ../.

Tres repeticiones

Los tres bloques reconstruidos permiten ascender desde el directorio de imágenes hasta la raíz del sistema de archivos.

etc/passwd

Completa la ruta hacia el archivo objetivo. Las líneas con formato root:x:0:0:... demuestran que se leyó el recurso solicitado.

Condición de éxito

El código 200, el cuerpo del archivo y el cambio a Solved forman una validación técnica y funcional del bypass.

Tipo de explotación: lectura arbitraria de archivos mediante bypass de eliminación no recursiva. No hubo ejecución de comandos, alteración de datos ni acceso fuera del laboratorio autorizado.

08 / MITIGACIÓN

Canonicalizar y confinar la ruta final

  • 1
    Usar identificadores indirectos

    Recibir un ID y resolverlo en el servidor evita que el cliente controle nombres o rutas del sistema de archivos.

  • 2
    Lista permitida estricta

    Aceptar únicamente nombres y extensiones esperados, sin depender de eliminar patrones posiblemente maliciosos.

  • 3
    Canonicalización y confinamiento

    Obtener la ruta real con una función equivalente a realpath() y comprobar que el resultado esté dentro del directorio autorizado.

  • 4
    Saneamiento iterativo

    Si se transforma la entrada, repetir la validación hasta que no aparezcan nuevas secuencias; aun así, priorizar la comprobación de la ruta canonicalizada.

  • 5
    Mínimo privilegio

    Ejecutar el servicio con una cuenta restringida y separar los archivos sensibles para reducir el impacto de una validación fallida.

  • 6
    Pruebas automatizadas

    Probar rutas anidadas, codificadas y normalizadas para verificar que ninguna transformación genere una secuencia válida después del filtrado.

12 / CONCLUSIÓN

Aprendizaje obtenido

El laboratorio mostró que transformar una entrada no garantiza que el resultado sea seguro. Al eliminar ../ una sola vez, el filtro produjo una nueva secuencia válida y permitió alcanzar un archivo fuera del directorio esperado. La práctica reforzó que la defensa correcta debe canonicalizar la ruta, comprobar su confinamiento y aplicar privilegios mínimos.
