Parcial 01 · Actividad 04

Una página demasiado convincente

Simulación local y autorizada de ingeniería social con Social-Engineer Toolkit, una página institucional ficticia y el módulo Credential Harvester Attack Method.

  • Estado: documentada
  • Fecha: 30/08/2026
  • Entorno: 127.0.0.1
  • Evidencias: 30 capturas

01 / OBJETIVO

Objetivo y alcance autorizado

Implementar y analizar, dentro de una máquina virtual de laboratorio, el recorrido de la información enviada por un formulario web hacia SET. La práctica permitió reconocer cómo una interfaz visual convincente puede influir en el usuario, comprobar la petición HTTP y proponer medidas técnicas y humanas contra el phishing.

Entorno seguro: la página “Nexo Campus”, el sistema, el usuario y la contraseña son completamente ficticios. La prueba se limitó a 127.0.0.1; no utilizó dominios externos, portales reales, datos personales, suplantación DNS, payloads ni código malicioso.

02 / CONCEPTO

¿Qué hace Credential Harvester?

Credential Harvester es un método de SET que hospeda o importa una página con formulario y registra, en el servidor local, los parámetros enviados por el navegador. En una campaña de phishing simula el punto en el que una persona entrega información a un portal falso.

Captura

Recibe y registra los valores que el navegador envía mediante una solicitud HTTP. En esta práctica se observaron scenario, username y password.

No es cracking

No adivina, descifra ni rompe una contraseña. La información fue escrita directamente en el formulario ficticio y enviada al servidor de laboratorio.

Servidor

SET atendió la página en el puerto 80 de la interfaz de bucle local y mostró el evento WE GOT A HIT al recibir la petición.

Persistencia

Los resultados se conservaron en harvester.log y en un informe XML aun después de terminar SET.

03 / CONFIGURACIÓN

Laboratorio y parámetros comprobados

  • ✓
    Kali Linux + SET 8.1.3

    Máquina virtual aislada y módulo Website Attack Vectors → Credential Harvester → Custom Import.

  • ✓
    Servidor exclusivamente local

    Dirección 127.0.0.1, puerto 80, APACHE_SERVER=OFF y WEBATTACK_SSL=OFF.

  • ✓
    Portal ficticio

    “Nexo Campus” incluyó nombre de sistema, usuario, contraseña, botón de ingreso y aviso de sesión expirada.

  • ✓
    Datos de demostración

    Usuario alumno_prueba04, contraseña ficticia Solo-Lab-2026! y escenario ACT04_LOCAL.

  • ✓
    Cierre seguro

    Se detuvo el servidor, se verificó que el puerto 80 quedara sin escucha y se restauró HARVESTER_LOG_PASSWORDS=OFF.

04 / FLUJO DE INFORMACIÓN

Del formulario al registro local

  1. Interacción: el usuario de prueba completa el formulario ficticio y selecciona “Ingresar al portal”.
  2. Solicitud: Firefox codifica los campos como application/x-www-form-urlencoded y genera un POST /.
  3. Transporte local: la solicitud viaja únicamente a 127.0.0.1:80.
  4. Recepción: el servidor de SET interpreta los parámetros y los muestra en la consola como una captura.
  5. Registro: SET escribe la información en el archivo de eventos y genera un reporte XML.
  6. Conservación: las copias de evidencia permanecen disponibles después de cerrar el servicio.

09 / INDICADORES

Señales para reconocer una página potencialmente fraudulenta

1. Dominio o URL

Variaciones, subdominios engañosos, IP directa o falta de coherencia con el servicio esperado.

2. Urgencia

Avisos de sesión expirada, bloqueo o pérdida de acceso que buscan reducir el análisis del usuario.

3. Solicitud inesperada

Petición de contraseña desde un mensaje o contexto que el usuario no inició.

4. Inconsistencias visuales

Errores de redacción, tipografía, alineación, iconos o colores que no coinciden con el portal habitual.

5. Navegación limitada

Enlaces secundarios, ayuda, privacidad o recuperación que no funcionan o llevan al mismo formulario.

6. Comportamiento del formulario

Destino, método o parámetros inusuales observables mediante herramientas de desarrollo.

7. Contexto y canal

Mensaje no solicitado, remitente inconsistente o enlace distinto al que se muestra.

Limitación

Ningún indicador aislado confirma fraude: los atacantes pueden usar HTTPS y copiar una interfaz con precisión. Deben evaluarse varias señales.

10 / CONTROLES

Medidas preventivas y de reducción de impacto

  • 1
    MFA resistente al phishing

    Passkeys o FIDO2 reducen la utilidad de una contraseña robada. Su límite es que requiere compatibilidad, enrolamiento y recuperación segura.

  • 2
    Gestor de contraseñas

    El autocompletado vinculado al dominio puede alertar ante una URL distinta. No protege si el usuario copia manualmente la clave.

  • 3
    Filtrado de correo y navegación

    Bloquea remitentes, enlaces o dominios conocidos. Puede fallar frente a infraestructura nueva y generar falsos positivos.

  • 4
    DMARC, DKIM y SPF

    Ayudan a autenticar el dominio remitente. No impiden mensajes enviados desde dominios parecidos o cuentas comprometidas.

  • 5
    Capacitación y canal de reporte

    Mejora la detección y la respuesta temprana. Necesita ejercicios periódicos y una cultura sin castigos por reportar.

  • 6
    Monitoreo y respuesta

    Detecta accesos anómalos, revoca sesiones y restablece credenciales. Actúa después del intento y requiere telemetría útil.

  • 7
    Mínimo privilegio y segmentación

    Limita el alcance de una cuenta comprometida. No evita por sí sola la captura inicial y exige mantenimiento continuo.

13 / CONCLUSIÓN

Aprendizaje obtenido

La práctica mostró que la apariencia no demuestra legitimidad: una página puede parecer institucional y, aun así, enviar los datos a un servidor distinto. La evidencia de red fue decisiva para relacionar la acción visible con la petición HTTP y los archivos de SET. También reforzó la importancia de trabajar con autorización, datos ficticios, alcance local, cierre comprobable y controles preventivos que no dependan solamente de la atención del usuario.
