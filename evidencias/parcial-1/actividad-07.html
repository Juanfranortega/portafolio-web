Explotando un Path Traversal con Burp Suite

Documentación del laboratorio “File path traversal, simple case”: interceptación de la solicitud, manipulación controlada del parámetro filename y validación del resultado.

  • Estado: completado
  • Fecha: 18/09/2026
  • Nivel: Apprentice
  • Evidencias: 13 capturas

01 / OBJETIVO

Comprobar una lectura de archivos fuera del directorio permitido

La práctica consistió en identificar el parámetro utilizado para cargar imágenes y modificarlo dentro de Burp Suite Repeater. El objetivo técnico fue recuperar el archivo /etc/passwd mediante una secuencia de recorrido de directorios y confirmar que el laboratorio reconociera la solución.

Entorno autorizado: la prueba se realizó exclusivamente dentro del laboratorio interactivo de PortSwigger Web Security Academy. El contenido se publica con fines académicos y defensivos.

02 / FUNDAMENTACIÓN TÉCNICA

¿Por qué ocurre un Path Traversal?

La vulnerabilidad aparece cuando una aplicación construye una ruta de archivo con datos controlados por el usuario y después la utiliza sin validar su destino canónico. En este laboratorio, la ruta vulnerable se encuentra en la consulta GET /image?filename=25.jpg: el servidor espera el nombre de una imagen, pero el parámetro filename también acepta secuencias de navegación entre directorios.

Clasificación

Corresponde a CWE-22 y se relaciona con OWASP A01: Broken Access Control, porque permite superar el límite lógico del directorio autorizado.

Impacto CIA

Afecta principalmente la confidencialidad. Si el mismo patrón se usa en funciones de escritura o borrado, también puede comprometer integridad y disponibilidad.

Contexto de datos

No se ataca una base de datos: se accede al sistema de archivos. Una aplicación puede obtener nombres desde una BD, pero debe validar la ruta real antes de abrir el recurso.

Variantes

Las defensas débiles pueden evadirse con rutas absolutas, eliminación no recursiva, doble codificación URL, validación parcial del inicio o bytes nulos.

03 / PROCEDIMIENTO · PREPARACIÓN

Configuración de Burp Suite y acceso al laboratorio

  1. Iniciar Burp Suite: se abrió Burp Suite Community Edition 2026.8 con un proyecto temporal y la configuración predeterminada.
  2. Preparar el Proxy: en la pestaña Proxy se mantuvo Intercept off para registrar la navegación sin detener cada solicitud y se abrió el navegador integrado.
  3. Leer la consigna: PortSwigger indicó que el laboratorio “File path traversal, simple case”, nivel Apprentice, debía resolverse recuperando /etc/passwd.
  4. Acceder al entorno: se abrió la tienda vulnerable; en ese momento el indicador todavía mostraba Not solved.

04 / PROCEDIMIENTO · CAPTURA

Localización de la consulta vulnerable

  1. Ajustar el filtro: en HTTP history se habilitó la visualización de imágenes, ya que el filtro inicial ocultaba ese tipo de contenido.
  2. Recargar la tienda: al navegar por los productos aparecieron múltiples solicitudes /image?filename=... con respuesta JPEG.
  3. Inspeccionar una petición: se seleccionó GET /image?filename=25.jpg y se verificó que el valor de filename llegaba directamente al servidor.
  4. Enviar a Repeater: mediante el menú contextual se copió la solicitud a Repeater para modificarla y reenviarla de forma controlada.

05 / PROCEDIMIENTO · EXPLOTACIÓN

Modificación, error inicial y respuesta vulnerable

  1. Conservar la línea base: Repeater recibió la petición original con filename=25.jpg.
  2. Modificar el parámetro: se sustituyó únicamente el valor de filename por ../../../etc/passwd.
  3. Diagnosticar el primer intento: un espacio agregado por error provocó HTTP/2 400 Bad Request y el mensaje No such file.
  4. Corregir y reenviar: al eliminar los espacios, el servidor respondió HTTP/2 200 OK y devolvió el contenido de /etc/passwd.
  5. Validar el resultado: PortSwigger mostró el mensaje “Congratulations, you solved the lab!” y el indicador oficial cambió a Solved.

06 / EXPLICACIÓN DEL PAYLOAD

../../../etc/passwd, componente por componente

../

Cada secuencia indica al sistema que suba un nivel desde el directorio actual. Tres repeticiones abandonan la carpeta donde la aplicación busca imágenes.

etc/passwd

Después del recorrido se solicita un archivo estándar de Linux que contiene información de cuentas locales. No almacena contraseñas en texto plano.

Normalización

El sistema operativo resuelve los segmentos .. antes de abrir el archivo. La aplicación vulnerable no verificó que la ruta resultante permaneciera dentro del directorio permitido.

Condición de éxito

El payload debía enviarse sin espacios. El estado 200 y las líneas con formato usuario:x:UID:GID:... confirmaron la lectura del archivo.

Tipo de explotación: lectura arbitraria de archivos mediante ruta relativa. No hubo carga de archivos, ejecución de comandos, alteración de datos ni acceso fuera del laboratorio autorizado.

08 / MITIGACIÓN

Defensa en profundidad contra Path Traversal

  • 1
    Evitar rutas proporcionadas por el usuario

    Usar identificadores indirectos y mapearlos en el servidor a archivos conocidos reduce la superficie de entrada.

  • 2
    Lista permitida estricta

    Aceptar únicamente nombres, extensiones y formatos esperados; rechazar separadores, rutas absolutas y secuencias de navegación.

  • 3
    Canonicalización y confinamiento

    Resolver la ruta real con una función equivalente a realpath() y verificar que comience dentro del directorio base autorizado.

  • 4
    Decodificación controlada

    Normalizar y decodificar una sola vez antes de validar para impedir que variantes URL codificadas evadan el filtro.

  • 5
    Mínimo privilegio

    Ejecutar el servicio con permisos restringidos y separar archivos sensibles para limitar el impacto si falla la validación.

  • 6
    Registro y pruebas

    Monitorear solicitudes anómalas y probar rutas relativas, absolutas, codificadas y entradas de borde durante el desarrollo.

Aprendizaje obtenido

El laboratorio demostró de forma práctica cómo una entrada no validada puede permitir la lectura de archivos sensibles.
